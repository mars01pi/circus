# Sandbox Guidelines

## 状态与边界

`circus-sandbox` 是 Rust library crate（包名 `circus-sandbox`，edition 2024）。当前提供 workspace 文件能力、`runtime::ResourceLimits` 资源请求校验，以及三个明确限定的 Linux 异步后端：Docker Engine + `runc`、containerd + `runc`（`io.containerd.runc.v2`、`overlayfs`），以及可选 `kubernetes` feature 下的 Kubernetes workload Pod（显式 kubeconfig、`runc` 节点运行时）。workspace 文件操作在 tempfile 新建的临时目录上，用 cap-std 目录句柄做相对路径读写；资源模型只校验请求值，后端负责显式配置和生命周期，不代表通用进程隔离或 Paseo 接入。

已实现：

- `Workspace` 同步 API：`new`、`write_file`、`read_file`、`create_dir_all`、`remove_file`、`cleanup`。方法会阻塞调用线程。
- `CodeSource::open` 只接受可信库调用方显式授权的源目录读取 grant；路径不是不可信租户请求的授权凭证。根打开遵循宿主路径解析，之后子项访问通过只读 cap-std 目录能力约束，不暴露源根路径。`copy_to_workspace(max_file_bytes, SnapshotBudget)` 逐文件复制到新建的自有 `Workspace`，源不被修改；不是接管或挂载宿主目录，也不改变 `Workspace::new` 的边界。
- 复制预算仅约束本次内容字节和文件/目录条目（根不计、空目录和零字节文件计入），精确等于上限允许；不是后续写入配额。拒绝源子项链接、非普通节点和不可移植名称，不按不可信 metadata 分配整个源树。`CodeCopyError` 清理失败分支保留部分工作区所有权以便重试。同步复制不保证源被外部修改时的一致快照或崩溃原子性；没有 Git metadata 特殊策略或隐式凭据共享。
- 既有 `CodeSnapshot` 是 `Workspace` 到进程内的内容捕获与新工作区恢复，另有显式 `save_file`/`load_file` 有界文件归档；不是外部源复制、进程/内存 checkpoint、工作区配额、加密、保留策略或租户隔离。调用方拥有归档宿主路径、存储和保留责任；不得把它改名为外部代码副本。
- 临时工作区由 tempfile 新建，不接受宿主目录，公开 API 不暴露工作区根路径。
- 跨平台拒绝空路径、绝对路径、`..`、Windows 盘符/UNC 前缀和反斜杠；通过后的访问走 cap-std，防止符号链接逃逸和基于路径字符串的 TOCTOU。
- 读写使用同一个 `max_file_bytes`。它是单个文件的上限：`new` 拒绝 `0` 和 `usize::MAX`，以便读取 `limit + 1` 时不溢出，也不按该上限预分配。它不是工作区总字节配额、文件数配额或宿主磁盘配额，当前也没有总配额 API。写满临时目录是宿主磁盘耗尽，不是 `LimitExceeded`。不要把这个参数写成沙箱配额，也不要在本 crate 增加总配额 API。后续真实进程或容器后端必须显式限制资源。
- `write_file` 不是原子替换。已关闭、非法路径、超限、缺失父目录和非普通文件在截断前返回，这些失败不修改已有文件。打开普通文件后先把长度设为 0 再写入；此后的 I/O 失败可能截断或留下不完整内容。不要写成原子写入，也不要为此增加原子 API。
- Unix 上 `read_file` / `write_file` 通过 cap-std `OpenOptions` 设置 `nonblock(true)` 再打开，因此 `open` 本身不等待 FIFO 对端。句柄级 `is_file` 在任何读取或 `set_len`/写入之前执行。路径 metadata 预检不是这个修复：工作区内指向 FIFO 的符号链接，以及打开前普通文件被换成 FIFO，都不得阻塞，并返回 `NotRegularFile`（保留调用方路径）。指向普通文件的工作区符号链接仍跟随。逃出工作区的符号链接仍是 cap-std 的 I/O 错误，不是新错误变体。Windows 不设置该标志；CreateFile 保持 write+create 且不预先 truncate，读取是只读打开。目录、FIFO、设备及其他非普通节点，包括指向它们的工作区符号链接，都是 `NotRegularFile`。
- `cleanup` 可重复调用；成功后文件操作返回 `Closed`。清理失败保留工作区归属，可重试，且不会标成已关闭。`Drop` 只做尽力清理，错误只有显式 `cleanup` 能观察到。
- `remove_file` 是 cap-std `Dir::remove_file`：对最终组件 unlink，不跟随该符号链接。非目录项都会删，包括普通文件、符号链接、FIFO 和 socket。目录返回 `Io` 且保留。文档若写成“只删除普通文件”，纠正文档；不要加删除前的类型预检，那会和 unlink 竞态。`NotRegularFile` 只属于读写。
- 同一 `Workspace` 的并发读写由内部 `RwLock` 保护。这只序列化本进程内对这一个值的调用，不是外部进程隔离，也不是 crash-safe 原子写。不要把这把锁写成原子替换或磁盘配额，也不要为此增加原子写入 API。
- `runtime::ResourceLimits` / `ResourceLimitsError` 是后端中立的资源值模型，无 `Default`。内存/工作区为正字节数且不超过 `i64::MAX`，CPU 为正 milli-CPU（`1000` 等于一个 CPU），进程数为正；工作区不超过内存，单文件上限不超过工作区。单文件上限为 `1..usize::MAX`，拒绝 `0` 和 `usize::MAX`，与 `Workspace::new` 一致。标量错误先于关联错误。校验不提供聚合准入/预留、内核强制或隔离，不附加宿主容量或 Docker 专用约束。
- `Workspace::capture_code_snapshot` 使用字节/条目预算捕获普通文件和目录，拒绝符号链接与特殊节点；`CodeSnapshot::restore` 创建独立工作区。`CodeSnapshot::save_file` 用同目录临时文件 rename 原子发布版本化自定界归档，`load_file` 以调用方 `max_file_bytes` 和预算逐项校验后分配，拒绝符号链接、特殊节点、重复/不可移植路径、截断和尾随字节。归档只含普通文件内容与目录，不持久进程/内存状态，不是工作区总配额、加密、保留策略或租户隔离；调用方拥有宿主路径和存储。agent 原生会话文件必须位于被捕获的 workspace 内才能随归档恢复。
- `agent-runner` 的 `TaskRequest.workspace: Option<TaskWorkspace>` 把调用方拥有的明文归档恢复到新建沙箱，并在销毁前捕获保存（失败也继续销毁）；`TaskRequest.agent_session` 经宿主控制器 `CIRCUS_RESUME_THREAD` 使用 Codex `thread/resume`，实际线程 ID 经 `agent_session` 线事件写入 `TaskOutput.agent_session`。每个任务仍重建沙箱：这不是进行中 turn 恢复、自动重试或常驻会话；Claude 会话续接显式拒绝。stdio bridge v1 的每个进程仍只执行一个任务，但请求可选暴露 `workspaceArchive`、预算与 `agentSession`，成功结果返回 `agentSession`；Paseo provider 据此每轮启动新进程并恢复同一归档。
- `Sandbox::spawn_process(ProcessRequest)` 是每沙箱一个的交互进程会话：显式 argv、相对 workspace 工作目录、显式环境覆盖、生命周期超时和每流输出上限。`ProcessSession` 的 stdin、有序 stdout/stderr 块、退出通知和取消彼此独立；文件、status、pause/resume 和 destroy 在进程运行期间仍可用。请求在入队前校验（`SandboxError::InvalidProcessRequest`），已有进程时再次 spawn 或一次性 `exec` 返回 `SandboxError::ProcessActive`。正常退出保留容器与 workspace；超时、输出超限、传输失败、会话 Drop 或 `cancel` 请求整体容器清理并通过 `ProcessExit::Terminated` 报告观测到的 `CleanupReport`。I/O 任务不删除容器、不修改 lifecycle 状态；它不是 TTY、进程组信号 API、分离式恢复或持久化机制。Docker/containerd 使用原生 exec；Kubernetes 经 `pods/exec` 附加，因该 API 没有 env 与工作目录字段，显式覆盖与 `chdir` 由独立的 Python `-I -B -c` argv trampoline 应用后再 `execvpe` 用户命令，覆盖值对同一沙箱内的其他进程可见但不被本 crate 记录。

- `Sandbox::create_with_recovery_id(backend, config, RecoveryId)` 使用调用方持久化的恢复标识；`Sandbox::create` 继续随机生成并由 `Sandbox::recovery_id()` 暴露。`RecoveryId` 只接受规范 36 字节小写连字符 UUID（`generate` 为 v4，`parse`/`FromStr` 拒绝大写、无连字符、前缀、空白和路径字符），校验在连接或分配前完成；实例名与 owner label 都是 `circus-sandbox-{id}`。同 id 重复创建不去重，可能在后端冲突。失去句柄后 `Sandbox::recover_orphan(backend, &id)` 只连接所选后端、不 prepare 镜像也不创建实例，并调用既有 `recover_owned(name, nonce, None)`：只有 owner label 匹配才删除，绝不按名称单独删除。返回 `Ownership::ConfirmedAbsent` 仅覆盖后端确认删除或本来不存在，`StillPresent`/`Unknown` 是未确认的尽力结果；没有 list-all API 或持久化注册表。`RecoveryId` 是可记录标签，不是秘密或授权凭证。

- `circus-sandbox-exec` 是工作区成员中的独立 stdio 代理二进制，不修改 `circus-paseo/`。它读取严格 JSON 配置（后端描述符、镜像策略/平台/期限、资源与 IO 限制、固定加固的 isolation、归档/状态路径、显式 guest 环境、进程期限与每流输出上限），恢复持久化 `RecoveryId` 的孤儿、按策略准备 Docker/containerd 镜像、在创建前加载有界归档、创建并启动沙箱、以一个 `ProcessSession` 转发原始 stdin/stdout/stderr，并在正常退出、SIGINT/SIGTERM、stdin EOF 或输出失败时捕获工作区、原子保存归档、销毁沙箱并更新保守 state。`StillPresent`/`Unknown` 恢复结果失败关闭；未确认清理保留 state 并以非零码退出。它不是 Paseo provider、模型代理、TTY、pause/resume、进程/内存检查点或凭证注入路径；Kubernetes 镜像拉取仍由 kubelet 负责，guest 环境不得含宿主模型凭据。用法与配置见 [sandbox-exec/README.md](sandbox-exec/README.md)。

仍未实现，不得写成现有能力：Kubernetes 真正 pause/resume provider（B03）、pids 限制、RuntimeClass 选择、NetworkPolicy/CNI 隔离、gVisor、Kata Containers、Firecracker、RPC、registry 认证、容器/VM 运行时快照（进程、客户机内存检查点）、工作区总配额执行、宿主磁盘配额、Paseo 接入。已实现且可写为现有能力：`Workspace`、`CodeSource` 独立代码副本、进程内 `CodeSnapshot` 及其有界 `save_file`/`load_file` 文件归档、Docker/containerd/Kubernetes 工作区文件快照与执行、Kubernetes workload Pod 的创建/就绪/exec/有界文件传输/工作区快照/交互进程/删除、固定提交 Git clone 与受控 worktree、本地 OCI 镜像解析、有界预启动租约池、交互进程会话、调用方持久化 `RecoveryId` 的孤儿恢复（只连接所选后端、owner-label 校验，绝不按名称删除）、后端中立统一 API、工作区成员 `circus-sandbox-exec` 的原始 stdio 代理（严格配置、归档恢复、孤儿恢复与确认清理），以及默认启用 `http` feature 的认证 JSON HTTP 传输（端点见 [HTTP API](docs/http-api.md)）。`ImageRequest` 默认 `LocalOnly`，仅显式 `IfMissing` 允许 Docker inspect 确认缺失后一次无认证拉取；`EnvironmentPlan` 遵循该请求策略，sandbox/HTTP 创建仍不拉取。镜像解析不隐式读取 Docker config/context 或环境凭据，无回退或重试；全流程共用 deadline，共享 cache 即使失败/取消仍可能改变且不删除镜像。它们都不是隔离、持久化或聚合资源预留的证据。Kubernetes Pod 支持工作区文件快照与交互进程，但会显式拒绝 `pause`/`resume`（类型化 `UnsupportedCapability`），不得用 Pod 重建冒充暂停。当前 Docker / containerd / Kubernetes slice 的范围和限制见 [Linux Docker + runc](docs/docker-linux-runc.md)、[containerd + runc](docs/containerd-runc.md)、[Kubernetes workload](docs/kubernetes-runc.md) 及 [ADR-0001](docs/adr-0001-docker-linux-runc.md)。不修改 `../circus-paseo/`。

Unix + `containerd` feature 另提供显式 `ContainerdImageRequest` / `prepare_containerd_image`，默认同样为 `LocalOnly`；只有 `IfMissing` 且 namespace 内 image record 缺失才允许一次无认证 daemon Transfer。连接、查询、可选 Transfer、元数据平台验证和不可变别名注册共用 deadline；不加载隐式凭据、不重试。Local-only 也可能注册 alias metadata；daemon Transfer/cache 可能在失败或取消后继续改变，库不删除共享镜像。该准备 API 不改变 sandbox/HTTP 创建仍不拉取的行为。

用户说明见 [README.md](README.md)，工程命令与门禁边界见 [docs/engineering.md](docs/engineering.md)，完整目标及交付记录入口见 [docs/delivery-plan.md](docs/delivery-plan.md)，安全扫描约定见 [安全说明](../.github/sandbox-security.md)。当前检出已有 Workspace crate、许可证策略、元数据/质量/安全/Rust 工作流，但开发约定和工作流存在仍然不是“全部领域已交付”或检查已通过。

## Architecture & Data Flow

当前调用路径包括：workspace 调用方 → `circus_sandbox::Workspace` → cap-std `Dir`，资源请求调用方 → `runtime::ResourceLimits`，以及容器调用方 → `api` → `lifecycle` → 私有 `infrastructure::Backend` 边界 → Docker Engine、containerd 或 Kubernetes API。交互进程调用方 → `Sandbox::spawn_process` → `lifecycle::process` → 后端 attach 传输；孤儿恢复调用方 → `Sandbox::recover_orphan` → 共享 `connect_backend` → 后端 `recover_owned`（不 prepare、不 create）；I/O 任务只搬运 stdin/stdout/stderr 和退出状态（Docker/containerd 原生 exec，Kubernetes 经 `pods/exec` 与 argv trampoline，三者共用同一 lifecycle 语义）。后端不泄露 bollard、containerd-client、tonic、`kube` 或 `k8s-openapi` 类型，所有状态修改与容器/Pod 删除由 lifecycle worker 串行拥有。

尚未实现的目标链路（Kubernetes 真正暂停/恢复、容器/VM 运行时快照、RPC 等）仍然只是规划，不得按目录存在推断能力；Docker/containerd 后端、Kubernetes workload Pod、预启动池、工作区文件快照（含 Kubernetes）、Git 准备、交互进程会话与 `src/http` 传输已实现。`src/http` 只做认证、路由、DTO 转换和租户注册表，所有状态修改仍进入 `lifecycle`。

## Code Conventions & Common Patterns

- Rust 模块、函数用 `snake_case`，类型与 trait 用 `PascalCase`；按职责内聚，不预先拆成七个 crate。
- API 使用领域请求、结果和错误；预期失败返回 `Result`，禁止用 panic 处理外部输入或吞掉清理失败。
- 生命周期显式建模合法转换；失败与取消必须有资源归属及回收路径，销毁应可重复调用。
- 通过构造参数注入后端、配置及外部服务；trait 只用于真实替换边界，不引入全局可变状态。
- 当前 workspace API 是同步且阻塞的。将来从异步上下文调用时必须 `spawn_blocking`；计划中的异步运行时仍只有 Tokio，不引入 async-std/smol 或第二套运行时。取消与超时不得遗留孤儿资源。阻塞任务开始后不能靠 abort 终止。
- 隔离级别、资源限制和权限由显式配置决定；禁止静默降级隔离，禁止默认把宿主目录或凭据暴露给沙箱。

  ```toml
  components = ["rustfmt", "clippy"]
  ```

- `Cargo.toml` 显式设置 `edition = "2024"`、`rust-version = "1.99.1"`、`license = "Apache-2.0"`。crate 禁止 unsafe。提交由 Cargo 生成的 `Cargo.lock`，不手写、不手改锁文件来绕过解析。构建使用 `--locked`，依赖 feature 按需开启，避免默认启用 `full`。多 crate 出现后再统一 workspace 依赖，不预建 workspace。
- Windows 本机开发使用 `x86_64-pc-windows-msvc`，需要 Visual Studio Build Tools 的 C++ 工具与 Windows SDK；Linux 隔离后端在 Linux 主机/虚拟机验证，不能把 Windows 编译成功视为隔离通过。仅为实际支持的平台安装 target；编辑器按需安装 rust-analyzer，不把它作为构建依赖。
- 工具链升级通过显式修改版本、核对依赖 MSRV、运行受影响检查及真实后端 smoke 验证完成；不自动追踪最新版本。[rustup 配置依据](https://rust-lang.github.io/rustup/overrides.html#the-toolchain-file)。

### 性能依据与兼容边界

- “性能最好”限定为目标平台、真实数据与相同语义下的测量结果。workspace 文件 API 可以运行，但尚无进程或容器沙箱，**没有本项目最快库的实测结论**。表中选型综合性能机制、维护与生态适配；网络/后端 SDK 不存在可脱离负载比较的统一性能排名。
- JSON 的具体取舍：sonic-rs 上游 README 提供 Xeon Platinum 8260 上 twitter/citm_catalog/canada 数据的基准，安全 `from_slice` 在这些结构体解析用例中快于 serde_json/simd-json；这是**上游结果，非本项目测量**。调研时仓库约 937 stars，是有实际采用但非最大众的性能型选择；stars 仅作采用度信号。[基准与运行条件](https://github.com/cloudwego/sonic-rs#benchmark)。
- sonic-rs 并非 serde_json 的无条件替代：非类型化 Value 的重复键行为存在差异，SDK 暴露的 serde_json 类型不能直接互换。[兼容说明](https://github.com/cloudwego/sonic-rs/blob/main/docs/serdejson_compatibility.md)。业务 JSON 当前经 serde_json 使用（axum `json` feature 与 DTO 解析必需）；sonic-rs 未引入，若未来引入必须整体迁移而非并存。
- 不把上游建议的 `-C target-cpu=native` 无条件用于分发产物；构建机与部署 CPU 可能不同，须明确目标指令集并验证可移植性。首次实现 JSON 路径时测量真实负载的吞吐、分配与尾延迟，同时验证重复键、数值精度、非法 UTF-8 和资源上限；不靠 unchecked API 或放松语义获得“更快”。

### 同类第三方库约束

- **尽可能避免使用两个同一类的第三方库：同一职责默认只保留一个直接依赖与一套业务使用方式。** 新增前检查现有依赖、标准库和已选生态能否满足；替换时迁移所有调用点并删除旧直接依赖，不保留双实现或兼容别名。
- 配套且职责互补的 crate 不算重复，例如 serde + sonic-rs、tracing + tracing-subscriber、tokio + tokio-util；后端 SDK 内部的 HTTP/JSON 实现也不等于允许业务层任意并用同类库。
- 无法消除的 SDK 类型约束、平台差异或传递依赖例外，必须在引入说明中记录原因、使用边界及去重不可行的证据；不能为去重破坏第三方兼容性，也不能以“传递依赖已存在”为由扩大直接使用。用 `cargo tree --duplicates` 与 `cargo tree -e features` 检查重复版本和 feature 来源；不同名称的同类库还需人工检查，命令输出不自动证明无重复。

## Runtime, Commands & QA

- Rust 核心使用上述 Cargo 工具链，不继承 Paseo 的工具链版本。服务入口尚未配置。`.github/workflows/sandbox-rust.yml` 显示名为 `Sandbox Rust`，检查名为 `rust (ubuntu-latest)`、`rust (windows-latest)`、`dependencies` 和 `codeql`。没有路径过滤，不调用 Paseo CI；`main` push、PR 的 `opened`/`reopened`/`synchronize`、merge queue 和 `workflow_dispatch` 都会启动。结果只记在对应 PR，不在本文声称当前提交已通过。命令在 `circus-sandbox/` 执行，rustup 读取本目录 `rust-toolchain.toml`。工作流存在不是服务可运行、隔离通过或分支保护已配置。`.github/workflows/sandbox-architecture.yml` 使用同一组触发条件，检查名为 `architecture (ubuntu-latest)` 与 `architecture (windows-latest)`。`.github/workflows/sandbox-docker.yml`（`Sandbox Docker`）只在 `pull_request` 与 `workflow_dispatch` 触发，在 GitHub 的 `ubuntu-latest` 上运行八个真实 Engine 忽略套件；它不要求本地 Docker，也不运行 Paseo。
- 本 crate 不允许 unsafe。库只导出已实现的 `Workspace` 文件 API 和 `runtime` 资源值模型，不预建其他空模块，也不创建空壳二进制来假装后端可用。
- 格式检查：`cargo fmt --check`（写回用 `cargo fmt`）。
- Clippy：`cargo clippy --locked --all-targets -- -D warnings`。
- 构建：`cargo build --locked`。
- 测试：`cargo test --locked`。公开文件 API 集成测试是 `cargo test --locked --test workspace`。连示例一起编译用 `cargo test --locked --all-targets`。可选后端还要分别验证 feature 关闭与开启：`cargo clippy --locked --all-targets -- -D warnings` 与 `cargo clippy --locked --all-targets --features kubernetes -- -D warnings`；默认构建不得要求 kube/k8s-openapi。

- `kubernetes (k3s)`：`.github/workflows/sandbox-kubernetes.yml` 在 `pull_request` 与 `workflow_dispatch` 触发，无路径过滤，权限仅 `contents: read`。在 `ubuntu-latest` 安装 Rust 1.99.1 与 k3s（官方脚本，`--disable=traefik`），等待节点 Ready，把 admin kubeconfig 只复制到该 job 的 `$RUNNER_TEMP`，用 `k3s ctr -n k8s.io images pull` 预拉取 `python:3.12-slim`，再以 `CIRCUS_KUBERNETES=1` 依次执行 `kubernetes_workload`、`kubernetes_snapshot` 与 `kubernetes_pool`（`--features kubernetes`、`--ignored --test-threads=1`）。它不证明真正暂停/恢复、RuntimeClass 或 VM 运行时；快照证据只覆盖工作区文件。

`deny.toml` 的许可证 allow 为 `Apache-2.0`、`MIT`、`Apache-2.0 WITH LLVM-exception`（winx 0.36.4 只声明这一表达式，不是 Apache-2.0 的别名）、`Unicode-3.0`（unicode-ident 1.0.27 是 `(MIT OR Apache-2.0) AND Unicode-3.0`）、`BSD-3-Clause`（matchit 0.8.4 经 axum 引入，`MIT AND BSD-3-Clause`）、`Zlib`（foldhash 0.1.5 经 containerd gRPC 依赖树的 hashbrown 引入）与 `ISC`（`kubernetes` feature 的 rustls 栈：ring 0.17.14 的 `Apache-2.0 AND ISC`、rustls-webpki 0.103.16、untrusted 0.9.0）。`exceptions` 为空。未列出的许可证失败。默认 `cargo deny --locked check` 的依赖图不含可选 kube/k8s-openapi；`cargo deny --all-features check` 使用同一 allow 列表。漏洞公告失败，且不得写入 ignore。yanked 为 deny，unsound 为 all，unmaintained 不忽略，unused-ignored-advisory 为 deny。来源只允许 crates.io；未知 registry 与 git 失败。通配版本 deny。`multiple-versions` 是 warn，不是 deny。
