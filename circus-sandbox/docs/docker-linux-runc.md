# Linux Docker + runc slice

This checkout implements an explicit local Docker Engine backend running a Linux image with the `runc` runtime. Creation goes through the backend-neutral `Sandbox::create(BackendConfig, SandboxConfig)` entry point. Sandbox creation never pulls images and does not expose bollard types. Callers provide the image, endpoint, resource limits, isolation policy, and output bounds; the owner label is generated internally per sandbox.

`SandboxConfig::new(limits, isolation, io_limits)` carries only values common to all backends. `BackendConfig::Docker` carries the endpoint string, image reference, and runtime name as plain data. Docker parses and validates them in private `infrastructure::DockerConfig` before any allocation: only a local Unix socket or Windows named pipe, only `runc`, a nonempty image, and at least 3 PIDs (the init/supervisor/command floor) are accepted. Failures are `SandboxError::BackendConfig(BackendConfigError)`. An absent local image is `SandboxError::BackendImageUnavailable { image }`; no pull is attempted. `Sandbox::create` rejects a backend that does not declare guest file transfer with `SandboxError::UnsupportedCapability`; `pause`/`resume`, workspace snapshots, and `spawn_process` check their own capability when called. Docker declares all four capabilities.

The adapter sets memory and swap, milli-CPU to nano-CPU, pids, a bounded tmpfs workspace, read-only root, `none` networking, `no-new-privileges`, and `ALL` capability drop. It creates no host binds, volumes, credentials, or ports. After creating the container and before reporting success or allowing `start`, it inspects `HostConfig` and verifies every constructed field: memory, `memory_swap == memory`, nano-CPUs, pids, read-only root, `network_mode=none`, `cap_drop` containing `ALL`, empty `cap_add`, `no-new-privileges:true`, empty binds/mounts/devices, exactly the configured tmpfs path with `size`/`uid`/`gid`/`nosuid`/`nodev`, the configured runtime, `init`, private IPC and cgroup namespaces, `oom_kill_disable=false`, `auto_remove=false`, restart policy `no`, and shm size. Any mismatch is a typed `SandboxError::PolicyMismatch { field, expected, actual }`, and the worker destroys the container or retains cleanup ownership through `CreationCleanupRequired`. Requested values are never reported as enforced without that inspection. Workspace files are staged from the existing capability-scoped `Workspace`. The guest file transport requires Python 3 and rejects symlinks during running-phase file operations.

`CommandRequest` uses argv form and a required timeout. stdout and stderr share one `output_limit_bytes` budget for the request: bounded chunks are counted together, output exactly at the limit is accepted, and the first byte over returns `SandboxError::OutputLimit { limit, phase: OutputPhase::Stdout | Stderr, .. }`. The lifecycle worker then reclaims the whole container and its descendants. A failed reclamation is reported through `Ownership`, never rewritten as success. The guest file helper has its own explicit accounting: `max_bytes + 1` of stdout to detect an over-limit file plus a 4 KiB stderr diagnostic allowance, with the combined budget equal to their sum; a stderr overrun is a transport failure, not a file-size result.

Command timeout, output overflow, and cancellation destroy the entire owned container so descendants cannot survive. Dropping the create future retains the generated name and owner label and recovers only a matching container. Operation cleanup errors retain ownership in the existing sandbox handle; retry `destroy` is required. Failed creation instead exposes the background cleanup receipt described below.

Operation deadlines are separate and configured through `IoLimits::with_deadlines(output_limit_bytes, command_timeout, file_timeout, lifecycle_timeout)` (`IoLimits::new` explicitly assigns the file deadline to all three classes). All must be positive. `command_timeout` is a ceiling on one exec: the worker enforces `min(request.timeout, command_timeout)`; a command deadline destroys the instance because the guest process may outlive its result. `file_timeout` bounds guest file operations and workspace capture/restore; those timeouts also destroy the instance because an in-flight transport cannot be resumed. `lifecycle_timeout` bounds `start`, `pause`, and `resume`; a timeout there destroys the instance because the engine may already have applied the transition. The same deadline bounds read-only `status` inspection, but a status timeout or cancellation does **not** destroy: it returns `TimedOut`/`Cancelled` with `SandboxOperation::Status`, `StillPresent`, and the retained instance id, and the phase stays retryable. `destroy` has no caller deadline and is never cancelled by dropping the future. Every timeout/cancellation error names the operation and reports observed ownership; cleanup failure is never reported as success.

The requested PID limit is enforced as supplied; the adapter does not silently increase it. Its budget includes the sandbox init, supervisor, commands, and any runtime/helper tasks charged to the container's PID cgroup, including temporary OCI exec startup tasks. Configuration validation requires at least 3 PIDs as a structural init/supervisor/command floor, not a guarantee that arbitrary commands or guest file operations can launch under every Docker/runc version. A low limit can therefore pass validation yet cause Docker to reject an exec. Such failures remain subject to the existing lifecycle safety cleanup described above; callers must handle reported errors and retained ownership.

The Docker integration test fixture requests 32 PIDs to leave room for temporary OCI startup tasks while exercising commands and guest file transport. This is an explicit test budget, not a product minimum or a universal launch guarantee. Applications must choose a PID budget that accommodates their commands and runtime's helper-task requirements.

Invalid command inputs are distinct from path failures: `SandboxError::Command(CommandError::EmptyArgv)`, `CommandError::InvalidTimeout { timeout }`, and `CommandError::InvalidOutputLimit { output_limit_bytes }` reject empty argv, zero timeout, and zero output bound before queueing. They preserve the phase, container identity, and staged files. A request above the configured output bound is separately rejected as `SandboxError::OutputLimit` with `OutputPhase::NotStarted` and `Ownership::StillPresent`; it does not execute or destroy the container. Actual command output overflow still destroys it.

`start` walks staging once and validates from metadata before starting the container: every relative path, each regular file's length against the per-file bound, and the aggregate payload total against the configured workspace bound. No payload is read during this walk, and the plan holds only relative paths and lengths, so its memory is proportional to the entry count rather than to payload bytes; a failed plan allocation is reported as a workspace I/O error. Each regular file is then opened once through the capability handle to verify readability and that its length still matches the plan; that preflight also closes before the backend start call, so ordinary staging errors still leave the sandbox `Created`. Once validation passes, the container starts and entries are transferred in the same walk order used for planning (each parent directory before its children): directories are created as entries, and each regular file is streamed from an already-opened cap-std-confined host handle through a bounded 64 KiB copy buffer. A single file is transferred at a time, so peak crate-controlled payload memory is one copy buffer, never the whole staged tree. This bound is on buffers this crate controls; it is not an administrator-visible memory limit and does not override the guest tmpfs, whose configured `size` remains the enforced workspace storage bound.

`SandboxError::Staging(StagingError::LimitExceeded { limit, actual })` reports the configured workspace byte bound and the first detected sum above it. Because the sum is now derived from metadata lengths before transfer, `actual` is the sum observed up to the entry that crossed the bound. Equality is permitted by this check. Defensive `StagingError::SizeOverflow { accumulated, next, limit }` retains the operands and bound if byte counting cannot fit `u64`. These are resource errors, not `RelativePath`. Both nested error types are exported through `api` and the crate root and retained as the standard error source; callers can match their variants rather than parse text.

A staging validation failure leaves the sandbox `Created`, retains its container identity and files, and allows removing or shrinking staged files before retrying `start`, or explicitly calling `destroy`. This payload check is not a host disk quota or a guarantee that tmpfs has room: filesystem metadata and allocation overhead can still cause a later upload to fail under the separately enforced tmpfs bound. A transfer failure after the container started is reported as the typed backend or workspace error and destroys the partially populated instance; a lifecycle-deadline timeout or cancellation during transfer does the same, and the phase is never reported as `Running` unless every entry was accepted.

The ignored integration tests require `CIRCUS_DOCKER_SANDBOX=1` and `CIRCUS_DOCKER_ENDPOINT`; they must run against a real Linux Docker Engine with cgroup v2. `CIRCUS_DOCKER_IMAGE` optionally overrides the default `python:3.12-slim` image and must refer to a local Linux image containing Python 3. The example is `docker_sandbox` and also requires an endpoint. Run `tests/docker_sandbox.rs` with `cargo test --locked --test docker_sandbox -- --ignored`, the bounded-staging suite (`tests/docker_staging.rs`) with `cargo test --locked --test docker_staging -- --ignored`, and the hardening suite (`tests/docker_hardening.rs`, sourced from `newtests/tests/docker_hardening.rs`) with `cargo test --locked --test docker_hardening -- --ignored`. The hardening suite is serialized internally because it observes the engine's global owned-container set. These tests are real-engine assertions and have not been executed in the environment that authored this change; the Docker CLI was unavailable there.

## Delete ownership and typed cleanup failures

Destruction reports one of three observed states: `Ownership::ConfirmedAbsent` (absence confirmed, staging removed), `Ownership::StillPresent` (inspection still finds the owned container), or `Ownership::Unknown` (neither absence nor presence could be confirmed). Only confirmed absence is success. The recovery protocol re-checks the owner label, issues a best-effort stop, and performs forced removal regardless of whether that stop succeeded, including on a stop transport failure. If the initial owner check fails transiently, a retained instance id is still used for the forced-removal attempt; an unconfirmed name is never removed directly, and a name carrying another label is never touched. After removal it inspects again, so a successful removal call that is contradicted by inspection is `StillPresent`, not success.

A failed `destroy` returns `SandboxError::CleanupRequired { instance_id, ownership, detail, failure }`. `failure` is a typed `CleanupFailure` standard error source: `Backend`, `StillPresent`, `Unknown`, `UnresolvedCreate`, or `Staging(WorkspaceError)`. The sandbox handle keeps its retained identity and staged files, so calling `destroy` again retries. Repeated calls after confirmed absence return `Ok` without contacting the backend; concurrent calls are serialized by the worker and never turn a failed attempt into a success. If local staging cleanup fails after the container is confirmed absent, ownership is `ConfirmedAbsent` but the attempt remains incomplete and retryable.

## Failed creation and cleanup receipts

`Sandbox::create` can return `SandboxError::CreationCleanupRequired { instance_id, source, cleanup }` when creation fails without returning a sandbox handle. This includes a rejected effective policy: the container was created but `PolicyMismatch` failed verification, and removal could not yet be confirmed. The boxed `source` preserves the original `SandboxError` (including `PolicyMismatch`) and its standard error chain. `cleanup` is a cloneable, debug-printable `CleanupReceipt`, exported from both `api` and the crate root. This differs from operation-level `CleanupRequired`, where the caller already owns a sandbox on which it can retry `destroy`.

The detached lifecycle worker retains both container identity and staging, and retries real cleanup with backoff from 100 ms to 30 seconds. Every retry updates the receipt. Dropping the create future, ready receiver, receipt, or a pending `wait()` does not stop that worker. A single not-found response while creation is unresolved is still not proof of absence: a late container could materialize. No receipt exposes the ownership nonce or permits adopting an arbitrary container ID.

`cleanup.status()` returns the latest actual cleanup report. `cleanup.wait().await` returns `Ok(report)` only after the worker reaches `Destroyed`, which requires both confirmed container removal/absence and successful staging cleanup. Do not refill pool capacity based merely on container absence or receipt delivery. Concurrent cloned receipts and cancelled/restarted waits are supported. If the worker disappears without confirmed completion, waiting returns `SandboxError::WorkerGone`; it must not be treated as safe capacity. Cleanup can remain pending indefinitely when the engine is unavailable or creation remains unresolved. These guarantees require the process and Tokio runtime to remain alive.

The same worker-owned progress channel is initialized before container creation and also tracks ordinary destruction and internal revocation. Before any cleanup attempt its report is conservatively `Unknown`. Internal pool revocation cancels the sandbox shutdown token, interrupting already-running operations, and returns a receipt without queueing behind those operations. The receipt confirms completion only after container and staging cleanup, including any retries.

```rust,no_run
use circus_sandbox::{BackendConfig, Sandbox, SandboxConfig, SandboxError};

async fn create_with_cleanup(
    backend: BackendConfig,
    config: SandboxConfig,
) -> Result<Sandbox, SandboxError> {
    match Sandbox::create(backend, config).await {
        Err(SandboxError::CreationCleanupRequired { source, cleanup, .. }) => {
            // Keep capacity reserved until both instance and staging are gone.
            cleanup.wait().await?;
            // Cleanup succeeded; creation still failed with its original cause.
            Err(*source)
        }
        result => result,
    }
}
```

Also note that `SandboxStatus` reports `instance_id` and inspected `enforcement` evidence. Each `EnforcementReport` field is optional; `None` means the engine did not report it. Requested limits are never copied into that structure as if enforced.

The policy-mismatch, unconfirmed-removal, and stop-transport-failure branches are exercised by private fault-injection seams inside the engine and lifecycle modules; the real-engine suite verifies successful creation policy, delete, missing-container, inspect-after-delete, aggregate output, command timeout, status timeout, and cancelled-create cleanup. The public configuration cannot force a real engine to silently alter its policy, so that branch is not claimed as a real-Docker observation.

Pre-create connection/image failures and settled creation failures whose cleanup is already confirmed keep their original error. Real Docker create-response-loss and staging-cleanup failure scenarios have not been exercised for this receipt change; the currently unavailable Docker environment is not evidence of successful cleanup. No simulated backend is used as a substitute for that integration proof.

## Workspace file snapshots

`Sandbox::capture_workspace_snapshot(budget, max_archive_bytes)` returns an `Arc<CodeSnapshot>` of regular files and directories, including empty directories. `SnapshotBudget::new(payload_bytes, entries)` requires positive limits; the workspace root does not count as an entry. The retained `max_archive_bytes: u64` name is historical: it bounds the transport encoding of the workspace manifest that enumerates the tree, not file payload. A zero value returns `SandboxError::Snapshot(SnapshotError::InvalidArchiveLimit)` before queueing. File payload is bounded separately by the configured per-file limit and by `budget`. Equality with any payload/entry cap is allowed.

In `Created`, capture reads host staging. In `Running`, the lifecycle worker enumerates only the configured workspace through the confined guest helper, checks the budgets, and reads each file individually. The container keeps running: `docker exec` is rejected on a paused container, so capture is a best-effort consistent read of a live workspace rather than a frozen checkpoint. Each file's observed length is compared with the manifest, and a concurrent change fails closed with `SnapshotError`; a partially written file is never reported as captured. A guest already `Paused` is briefly resumed for enumeration and paused again after success or an ordinary validation/budget failure. Other phases reject capture with `InvalidPhase`.

The tmpfs workspace is invisible to Docker's archive API: `download_from_container` for a `--tmpfs /workspace` root returns a stream containing only the mountpoint itself, with none of the files below it. Capture therefore reads the tree through the same confined `python3 -I -B` file helper that serves ordinary file operations. The helper lists each directory through an `O_NOFOLLOW` directory descriptor and inspects every entry with `follow_symlinks=False`, so it never resolves a link. A symlink, FIFO, device, socket, hardlinked file (`st_nlink != 1`), non-UTF-8 name, or non-portable relative name (empty, `.`, `..`, backslash, or drive-prefix component) fails closed with a typed exit status instead of being skipped.

The manifest is sorted by path bytes and NUL-delimited, one record per entry: the kind byte `d` or `f` followed by NUL, the UTF-8 workspace-relative path followed by NUL, and for files the decimal byte size followed by NUL. The root is never listed. The host decodes it strictly: a truncated record, unknown kind, non-canonical size, non-UTF-8 or non-portable path, duplicate path or unsorted path is a protocol failure. The helper enforces the caller's manifest byte bound (limit exit) and entry bound (typed entry-limit exit) while it walks and serializes.

Budgets are checked against that metadata before any payload byte is transferred, in a fixed order: entry count (`SnapshotError::EntryLimit`), each file's declared size against the configured per-file limit (`SnapshotError::Workspace(WorkspaceError::LimitExceeded)`), then the running total against the capture budget (`SnapshotError::ByteLimit`). Only then is each file read with the per-file limit as its bound, and a payload that does not match its declared size fails the capture. Snapshot ordering matches the manifest.

`Sandbox::restore_workspace_snapshot(Arc<CodeSnapshot>)` is only valid in `Created`. It shares the immutable snapshot rather than cloning its file payloads. It validates the target configuration's per-file and workspace payload bounds, creates replacement staging, and explicitly removes old staging before committing the replacement. It does not start a container or overwrite a running guest. Validation failures preserve old staging. If old cleanup fails, old staging remains owned and installed, but may have been partially removed; replacement staging is explicitly cleaned. A replacement cleanup failure is returned as nested `SnapshotError::RestoreCleanup`, owning that workspace for retry. Domain capture cleanup failures likewise retain temporary workspaces.

Both APIs serialize with all other sandbox operations and use the configured file timeout for the complete operation. Cancellation and timeout invoke whole-container cleanup, not process-only cancellation, and retain ownership when removal cannot be confirmed. Engine resume/re-pause, workspace enumeration and read failures also use owned cleanup. Ordinary unsafe-node, validation, budget and target-limit failures use `SandboxError::Snapshot`; the source keeps its original phase before that failure is returned and stays usable. `CleanupRequired` preserves container identity for explicit `destroy` retry.

The deadline initiates cancellation, not a guarantee of cleanup-completion time. Already-started bounded local filesystem work is drained rather than detached, and produced replacement staging is explicitly removed before container cleanup. Guest enumeration and payload reads can be dropped promptly. Only the lifecycle worker installs staging, never a detached filesystem task. `SandboxError::SnapshotInterrupted { interruption, snapshot }` preserves a timeout/cancellation or lifecycle failure together with a domain failure and its cleanup-owned workspace.

Snapshot values remain process-local. `CodeSnapshot::save_file` and `load_file` optionally add a bounded, versioned durable file archive for a trusted caller-supplied host path; that archive contains regular-file contents and directories only and validates caller budgets before allocation. It is not process/memory state, VM checkpointing, CRIU, Docker commits, a quota, encryption, retention, or tenant scoping, and this backend does not use it implicitly. The readonly root and tmpfs workspace mean Docker commit would omit workspace writes; reading the tmpfs through the guest helper is required.

## Prestarted single-use sandbox pool

`PoolConfig::new(BackendConfig, SandboxConfig, capacity, Option<Arc<CodeSnapshot>>, lease_ttl: Duration)` rejects zero capacity and requires an explicit positive lease TTL. TTL begins at lease allocation, not pool warmup or acquire queue entry. Expiry requests revocation and interrupts an in-flight command; it is not instantaneous proof of container absence. Await confirmed cleanup before treating capacity as reusable. `SandboxPool::create(config).await` warms the entire capacity before returning: each fresh container is created, its baseline snapshot restored while Created, started, and checked for actual Running status. The pool is backend-neutral and accepts either a Docker or a containerd `BackendConfig`; each slot still uses the real backend lifecycle (Docker/runc or containerd/runc) and this API does not checkpoint a process or eliminate startup cost. `examples/docker_pool.rs` observes cold create + restore + start, full pool warmup, and acquisition separately with `Instant`, executes the restored program bytes, then explicitly releases and shuts down. Individual timings are not a guaranteed speedup.

`SandboxPool` clients are cloneable, but `PoolLease` is not. `acquire(&self, Duration).await` requires a positive explicit deadline, returns `PoolError::AcquireTimeout` on timeout, and serves live waiters FIFO. Cancelled waiters do not consume slots. `PoolLease::sandbox()` borrows the real `Sandbox`; it does not export a clonable owning handle. Every lease is single-use: release, Drop or expiry destroys that container, and only confirmed absence permits fresh replacement from the immutable configuration and optional baseline. No dirty container is reset or reoffered. Baseline contents are explicitly authorized shared input, not discovered secrets or a credential-scanning policy. Never use a previous tenant's changes as the baseline.

`status().await` reports public disjoint `capacity`, `ready`, `creating`, `leased`, `retiring`, `cleanup_required`, `absent`, and `closing` fields; all slot categories including absent sum to capacity. Cleanup failures continue occupying capacity rather than allowing unbounded replacement. `ResourceLimits` applies to each container, not aggregate host reservation/admission. A slow refill does not require suspending ready acquisitions.

`release(self).await` observes destruction of the released container; Drop only requests it. `shutdown().await` rejects new acquisitions, cancels queued acquisitions, and **revokes outstanding leases**, destroying their containers even if lease handles remain alive. It is idempotent and succeeds only after every owned container is confirmed absent. Cancelling the shutdown future does not stop the cleanup worker or discard in-flight create results. Last-client Drop requests shutdown but is not proof of cleanup; lease handles do not keep that last-client guard alive. The worker retains unresolved resources and retries removal. If construction returns `PoolError::CleanupRequired { pool, source }`, retain that returned cleanup owner and call `pool.shutdown().await` to observe confirmation.

The default local image is `python:3.12-slim`, optionally overridden with `CIRCUS_DOCKER_IMAGE`; it must already exist and contain Python 3. Fixtures and the example request 32 PIDs. On Windows, explicitly set the same variables in your shell with endpoint `npipe:////./pipe/dockerDesktopLinuxEngine`. Tests check baseline bytes and empty directories, private-marker isolation across fresh leases, SDK inspect HTTP 404 after release/drop/shutdown/expiry, bounded concurrent leases and timeouts, cancellation, TTL revocation of a command awaiting a long-running Python child followed by fresh refill, retained preparation-error sources, and an unrelated surviving container. They are opt-in tests, not evidence that this checkout has exercised Docker successfully.

Image resolution is available through `environment::prepare_docker_image`. `ImageRequest::new` defaults to `ImagePullPolicy::LocalOnly`: inspect the original reference on the explicit endpoint and return an immutable image ID and actual platform, or a typed failure. `.with_pull_policy(ImagePullPolicy::IfMissing)` permits one unauthenticated SDK pull only after inspect reports not found. Cached platform mismatches and other inspect failures never pull; there is no retry or fallback. Pull requests select linux/arch[/variant]; final inspection of the same original reference verifies OS/architecture, not variant. Use the returned immutable ID with `BackendConfig::docker`, not a mutable tag.

The SDK pull stream is consumed to completion before final inspection; its `errorDetail` entries are failures even when the detail has no message. No pull progress ID is used as the prepared image identity.

Connection negotiation, initial inspect, pull stream consumption, and final inspect share the request's whole-operation deadline. The library never loads Docker config/context or environment credentials and passes no registry credentials. Failure, timeout, or cancellation may still mutate the shared daemon cache; dropping the resolution future spawns no library background tasks and never removes shared images. Registry authentication remains unsupported. Git checkout is a separate workspace capability, not part of this backend.

## Environment preparation plans and identity

`environment::EnvironmentPlan::new(ImageRequest, Vec<PrepareStep>)` defines an explicit ordered preparation plan. `PrepareStep::new(argv, PinnedVersion, timeout, output_limit_bytes)` accepts a separate argv vector only: there is no shell, string interpolation, inherited host environment, or credential injection, and every argument is passed as a distinct exec argv element. `PrepareStep::unpinned(...)` exists so unpinned input can be represented and rejected by `EnvironmentPlan::new` with `PlanError::UnpinnedInput { index }` before any Docker connection or container allocation. A plan also refuses an empty step list. Each step's output bound must not exceed the configured `SandboxConfig::output_limit_bytes()`.

`EnvironmentPlan::execute(SandboxConfig).await` resolves the explicit image using its `ImageRequest` pull policy (default LocalOnly), creates and starts one owned sandbox, executes the steps in order with the public exec API, destroys the sandbox, and waits for the lifecycle cleanup receipt to confirm both container absence and staging removal. A non-zero exit stops the plan and returns `PreparationError::StepFailed { index, argv, exit_code, stdout, stderr, output_limit_bytes, cleanup }`; `stdout` and `stderr` are bounded by the step's `output_limit_bytes`. A deadline or transport failure returns `PreparationError::StepTimedOut` or `PreparationError::StepOperation`, retaining the step index and argv. When cleanup cannot be confirmed, the step error's `cleanup` field records the detail; a successful return always implies confirmed cleanup. Cancelling or dropping the execute future relies on the sandbox lifecycle owner's Drop revocation; cleanup continues in its detached worker, but the dropped future cannot report the outcome. Creation failures that expose `SandboxError::CreationCleanupRequired` are observed through that receipt before this module reports a typed preparation failure. Shared image-cache mutations are not part of sandbox cleanup.

`PreparedEnvironment` records the immutable image ID, repository digests, requested platform, exact pinned steps, and bounded observations. `EnvironmentId::new(image_id, repo_digests, platform, steps, tenant)` and `PreparedEnvironment::identity(TenantDomain)` derive an opaque value with SHA-256 (FIPS 180-4) over canonical serialization format version 1: the image ID, repository digests as a sorted set, platform OS/architecture/variant (Docker image inspection reports only OS and architecture, so a variant is hashed but not verified against the manifest), every ordered step's exact argv and pinned version, and the caller-supplied tenant security domain. Changing any included input invalidates the old identity; equivalent inputs, including a different repository-digest order, produce the same value. The tenant domain is required so that equal image and step input cannot collide across trust domains. The digest excludes Docker endpoint, host paths, environment variables, credentials, timeouts, output bounds, and observed output, and `Display`/`Debug` reveal only the 64-character lowercase hexadecimal digest. This is identity derivation only: no cache, registry, persistence layer, or lookup service is implemented, and no image retention is provided beyond the daemon's own cache.

Identity tests run with the normal test suite. The real preparation tests are ignored and require the same explicit environment as the other Docker integration tests, plus `CIRCUS_DOCKER_ARCH` for the platform:

They are not evidence that this checkout has exercised Docker.

## Interactive processes

`Sandbox::spawn_process(ProcessRequest)` returns a `ProcessSession` after the backend attaches the process. Creation uses the neutral entry point, `Sandbox::create(BackendConfig::docker(endpoint, image, "runc"), SandboxConfig::new(limits, isolation, io))`; the process API names no backend SDK type. The request supplies argv, an optional workspace-relative working directory, explicit environment overrides, a lifetime timeout, and a total output limit for each of stdout and stderr. The output limit cannot exceed the configured `IoLimits::output_limit_bytes`. Environment names must be portable identifiers and values must be NUL-free. No host environment is copied; the image environment still applies. Environment overrides are not a secret store or an outbound network policy. A relative working directory uses container filesystem semantics, including container symlinks.

`ProcessRequest::validate` rejects malformed requests before queueing: no exec is created, no deadline applies, and phase and ownership are unchanged. That covers empty argv, NUL bytes, zero or unrepresentable timeouts, zero or `usize::MAX` output limits, traversing or absolute or non-slash working directories, and non-portable environment names. A request above the configured output bound is rejected the same way. Both use `SandboxError::InvalidProcessRequest { reason }` (`check_relative` keeps returning its own `ConfigError` for a rejected working directory).

Use `write_stdin` repeatedly to send protocol messages and `next_output` to receive raw `ProcessOutput::Stdout` / `Stderr` chunks. Chunks may split lines or UTF-8 characters. `close_stdin` sends EOF; it does not terminate the process. Drain output concurrently with input and `wait`: the output queue holds eight chunks of at most 16 KiB each, then applies backpressure. Input calls are serialized and copied in 16-KiB chunks through a bounded queue. The transport may also retain an in-flight Docker frame. Total output limits and the lifetime timeout remain active under backpressure and while the container is paused.

One interactive process is admitted per sandbox. A second process and one-shot `exec` return `SandboxError::ProcessActive` until lifecycle records completion. File operations, status, pause/resume, and destroy remain available while the process runs. The I/O task reports completion to the lifecycle owner; it never deletes containers or changes sandbox state itself. Attachment uses the configured file deadline; a deadline or cancellation destroys the owned instance because the exec may already have been accepted.

`wait` is repeatable and returns `ProcessExit::Exited` with the actual exit code, including nonzero codes. A normal exit preserves the container and workspace. Cancelling a `wait` or `next_output` future does not cancel the process. Dropping a session, calling `cancel`, or abandoning an accepted stdin operation requests whole-container cleanup. Timeout, output overflow, and transport failure also require cleanup. `ProcessExit::Terminated` reports the reason and observed `CleanupReport`; if ownership is unknown, retain the sandbox and retry `Sandbox::destroy`. `Drop` only requests cleanup while the Tokio runtime is alive; process crashes do not provide durable reconciliation.

Agent turn cancellation belongs in the agent's stdin protocol. Session cancellation and sandbox destruction force-remove the container and lose its tmpfs writes, including writes by descendant processes. Export results before deliberate destruction. There is no detached process recovery, TTY, process-group signal API, model access, or Paseo integration in this slice.

Run the two-message example with a local Python image and an explicit endpoint:

```bash
CIRCUS_DOCKER_ENDPOINT=unix:///var/run/docker.sock \
  cargo run --locked --example interactive_process
```

Run the existing backend checks and the interactive process tests against a real Linux engine:

```bash
CIRCUS_DOCKER_SANDBOX=1 CIRCUS_DOCKER_ENDPOINT=unix:///var/run/docker.sock \
  cargo test --locked --test docker_sandbox --test docker_process -- --ignored --test-threads=1
```

The interactive tests cover repeated input, separate output streams, exit codes, concurrent file and lifecycle operations, one-process admission, output backpressure, timeout, cancellation, and owned-container cleanup. They are ignored without explicit invocation; ordinary Cargo test success is not Docker runtime evidence.

## Instrumentation and its limits

`Sandbox::create_with_metrics(backend, config, metrics)` and `PoolConfig::with_metrics(metrics)` accept a caller-created `SandboxMetrics` handle. The lifecycle worker, pool worker, and Docker backend record fixed counters into it: create success/failure, pending and completed create cleanup, operations by fixed kind and outcome, cleanup attempts/failures, pool ready/leased/retired/refilled transitions, snapshot captures/restores, and process sessions started/ended by termination kind. `SandboxMetrics::snapshot()` copies plain values and does not reset anything. Without a handle every recording method is a branch-only no-op; there is no global registry and no label chosen by a caller or tenant. Cumulative counters saturate at `u64::MAX` and the pending-cleanup gauge saturates at zero.

The same lifecycle, pool, and backend points emit `tracing` events with stable event names: `sandbox.create.started`/`completed`, `sandbox.capability.unavailable`, `sandbox.transition.completed`, `sandbox.exec.completed`, `sandbox.process.opened`/`closed`, `sandbox.snapshot.capture.completed`/`restore.completed`, `sandbox.cleanup.attempted`, `sandbox.cleanup.retry`, `sandbox.create.cleanup.completed`, the `pool.*` lease and slot events, and the `backend.*.completed` events, plus `sandbox.create` and `backend.create` spans. Fields are limited to fixed labels, counts, booleans, durations, exit codes, and the sanitized basename of `argv[0]`.

Excluded on purpose: environment values, full argv, guest file contents, host paths, image credentials, and endpoint URLs with credentials. Error events carry a fixed `error_kind`, never the backend message, because backend text can embed paths. An unavailable capability (`sandbox.capability.unavailable`, `error_kind = "unsupported_capability"`) is distinct from cleanup that is still owed (`cleanup_pending = true`, `cleanup_required = true`, and the `create_cleanup_pending` gauge).

This crate installs no global `tracing` subscriber and provides no health, readiness, or metrics HTTP endpoint. Collecting or exporting events is the embedding application's responsibility. Instrumentation is not evidence that a real Docker Engine ran: the ordinary test suite covers event fields and counters without Docker, and the opt-in Docker tests remain the only runtime evidence.
